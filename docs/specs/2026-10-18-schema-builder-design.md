# Design: Schema Builder and JSON Schema Export (RuleLoom.Schemas)

**Issue:** [#92 Schema builder and JSON Schema export (RuleLoom.Schemas)](https://github.com/STotev/RuleLoom/issues/92)
**Parent PRD:** [#87 Schemas and contexts (0.6)](https://github.com/STotev/RuleLoom/issues/87) (user stories 1–17, 22)
**Date:** 2026-10-18
**Status:** Approved (HITL, decisions below)

---

## Problem

A central rules service doesn't know the events it handles: their fields, types and meaning. Producers already have
DTOs for their events, so they should describe each event in a few lines, with everything else inferred, and ship the
description as a standard document that the central service (and later a UI) can read.

## Package

New **`RuleLoom.Schemas`** package (namespace `RuleLoom.Schemas`), with no dependencies beyond the BCL (reflection,
System.Text.Json). Producers reference only this package: no engine, no DI. Tests go in a new
`RuleLoom.Schemas.Tests` project.

## Defining a schema

```csharp
public sealed class OrderPlacedSchema : EventSchema<OrderDto>
{
    public OrderPlacedSchema()
    {
        Event("OrderPlaced").Label("Order placed").Description("A customer placed an order.");

        Field(o => o.Total).Label("Order total");
        Field(o => o.Status).Description("Placed or paid.");
        Field(o => o.CustomerId).Ignore();          // technical: used to load the customer, not offered to rule authors
        Field(o => o.InternalNotes).Ignore();

        Context("customer").ReferencedBy(o => o.CustomerId).Label("Customer");
        Context("shipping-zone").ReferencedBy(o => new { o.Address.Country, o.Address.Postcode });
        Context("calendar");                        // needs no reference (e.g. public holidays)
    }
}

EventSchemaDefinition schema = new OrderPlacedSchema().Build();

var schemas = new EventSchemaCollection().AddFromAssemblyOf<OrderPlacedSchema>();
string json = schemas.ToJson();                                        // a JSON array of event documents
IReadOnlyList<EventSchemaDefinition> parsed = EventSchemaDefinition.ParseMany(json);
```

- **`Event(name)`** is required; building without it throws. `Label`/`Description` describe the event.
- **`Field(expression)`** points at a property, at any depth (`o => o.Customer.Tier`), and configures `Label`,
  `Description` or `Ignore()`. Configuring the same field twice merges (the last value wins). An expression that isn't a
  property chain throws.
- **`Context(name)`** declares a context the event **relates to** (names ignore case; duplicates throw): an entity rules
  use as `@name`, loaded by the context provider registered under that name (#91). The event schema describes the
  relation, not the context's fields: those are described where the provider is registered (#93 follow-up slice), so
  each context is described once, where its data really comes from. `Label`/`Description` describe the relation.
- **`ReferencedBy(expression)`** says how the event refers to the context: a subject property (`o => o.CustomerId`) or,
  for a composite reference, an anonymous object of properties (`o => new { o.Address.Country, o.Address.Postcode }`,
  EF Core style). Paths are mapped to JSON names; part names follow the naming policy. The engine resolves the
  reference from the event and passes it to the provider (#93), so one provider can serve several contexts and events
  (e.g. `fromAccount`/`toAccount`). It's optional: contexts like a business calendar need none. A reference may point at
  an ignored field (keys are often technical); a property that isn't serialized throws.
- The configuration runs in the constructor (FluentValidation style). `Build()` (also used by the collection) runs
  inference, applies the configuration and returns an `EventSchemaDefinition`. Configuring a field that inference didn't
  produce throws (see Generation), and so does configuring a field inside an ignored one, whatever the call order.
- **`EventSchemaCollection`** gathers schema classes (`Add<TSchema>()`, `Add(schema)`, `AddFromAssemblyOf<T>()` /
  `AddFromAssembly(assembly)`: public, non-abstract, non-generic classes with a parameterless constructor), builds them (duplicate
  event types throw) and writes them as JSON.
- **Labels are only what the developer configures** (no labels derived from names): a `title` is written only where
  `Label(...)` is set, and the model's `Label` is `null` otherwise. UIs fall back to the JSON name.

## Generation

Schemas are generated by **System.Text.Json's built-in `JsonSchemaExporter`** (.NET 9+), so `RuleLoom.Schemas` stays
dependency-free and each schema describes **how the producer's DTO is serialized**: property names after the naming
policy, `[JsonIgnore]`, enum converters, nullability, formats (`date-time`, `date`, `uuid`), arrays and dictionaries.

- **Serializer options**: `JsonSerializerDefaults.Web` by default (camelCase, as ASP.NET Core and `HttpClient`'s JSON
  helpers use); producers pass their own to `Build(options)` / `new EventSchemaCollection(options)`, e.g. with
  `JsonStringEnumConverter` so enums appear as names.
- **Normalization** so the schema describes what is *sent*: generated without `AllowReadingFromString` (written numbers
  are numbers; otherwise they appear as `["string","number"]` with a pattern), with null-oblivious types treated as
  non-nullable (list items, the root), and the root typed `"object"`.
- **RuleLoom's layer** is applied to the generated document: `$schema`, `x-ruleloom-event`, configured titles and
  descriptions (event, fields, contexts), ignored fields removed, and `x-ruleloom-contexts`.
- **`Field(o => o.Customer.Tier)`** is mapped to the JSON path through the serializer's type info (so it follows the
  naming policy). Configuring a property the serializer doesn't write (`[JsonIgnore]`) or that has no place in the
  schema (inside a dictionary, below a cycle) throws when building.
- **Repeated types**: the exporter writes a `$ref` for every repeat of a type, also to a *sibling* property. Sibling
  references are copied in place after generation, so the only `$ref`s left point at an ancestor (a real cycle).
  Removing an ignored field therefore can't leave a dangling reference. When reading, a cycle `$ref` takes its type from
  its target, without fields.
- **Untyped values** (`object`, `JsonElement`, `JsonNode`) are the schema `true` (or `{}` once labelled) and read as
  `FieldType.Any`; an array without `items` (`List<object>`) has items of any value.
- **Nullable string enums** are written as `"enum": [..., null]` without `type`; the `null` makes the field nullable.
- **Numbers written as strings** (`JsonNumberHandling.WriteAsString`) are typed `["string","number"]`; they're read as
  strings, which is what is sent.
- Serializer options are prepared once per **read-only** options instance (cached), so System.Text.Json's metadata is
  shared by every schema built with them; options that can still change are prepared on each build. A collection makes
  one read-only copy for all its schemas.
- **Named floating-point literals** (`AllowNamedFloatingPointLiterals`) come out as `anyOf` (number or `NaN`/`Infinity`);
  the `anyOf` branches' types are read, so they stay numbers.
- Field names in the model are the **JSON names**; rule paths match them ignoring case.

## Model

Immutable records built by the builder and read back from JSON:

- **`EventSchemaDefinition`**: `EventType`, `Label`, `Description`, `Fields`, `Contexts`; `ToJson()`, `Parse(json)`,
  `ParseMany(json)`.
- **`FieldDefinition`**: `Name`, `Type` (`FieldType`), `IsNullable`, `Label`, `Description`, `EnumValues`, `Fields`
  (objects), `Items` (arrays: the element's definition).
- **`ContextDefinition`**: `Name`, `Label`, `Description`, `ReferencedBy` (`ContextReference`: a single `Path`, or named
  `Parts` for a composite reference; `null` when there's none).

## JSON format

Each event is a **JSON Schema 2020-12** document for its subject, with RuleLoom keywords for what JSON Schema doesn't
cover. Labels use the standard `title`, descriptions `description`.

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "x-ruleloom-event": "OrderPlaced",
  "title": "Order placed",
  "description": "A customer placed an order.",
  "type": "object",
  "properties": {
    "total": { "type": "number", "title": "Order total" },
    "status": { "type": "string", "enum": ["Placed", "Paid"], "description": "Placed or paid." },
    "placedAt": { "type": "string", "format": "date-time" },
    "note": { "type": ["string", "null"] },
    "address": { "type": "object", "properties": { "country": { "type": "string" }, "postcode": { "type": "string" } } },
    "lines": { "type": "array", "items": { "type": "object", "properties": { "sku": { "type": "string" } } } }
  },
  "x-ruleloom-contexts": {
    "customer": { "title": "Customer", "x-ruleloom-referenced-by": "customerId" },
    "shipping-zone": { "x-ruleloom-referenced-by": { "country": "address.country", "postcode": "address.postcode" } },
    "calendar": {}
  }
}
```

- A context entry describes the relation only (title, description, reference); context fields aren't in event schemas.
- Ignored fields are left out.
- Reading JSON back accepts what the serializer writes; other keywords are ignored. A schema round-trips without loss:
  `Parse(schema.ToJson())` gives equal definitions (the records compare their lists and dictionaries by content). Every
  malformed document (no or an empty `x-ruleloom-event`, unknown or non-string `type`, a `$ref` outside the document,
  duplicate keys, context names differing only in case) throws `JsonException`.
- **One document per event.** A collection writes a JSON array of event documents; `ParseMany` reads it back.

## Test plan

- **Builder:** event name required, configured labels and descriptions only, nested `Field` paths, `Ignore`, merging repeated
  configuration, invalid expressions, contexts (single and composite references, no reference, reference to an ignored
  field, invalid and unserialized references, duplicates), assembly collection and individual adds.
- **Generation:** types and formats (string, integer, number, boolean, date-time, date, uuid, enums as numbers and with
  `JsonStringEnumConverter` as names), nullability, nested objects, arrays, dictionaries, cycles (`$ref`, also inside
  in the subject), `[JsonIgnore]`, Web defaults vs custom options (naming policy), numbers not typed as strings.
- **JSON:** the output shape (keywords, `title`, `format`, nullable types, contexts), lossless round trip, parsing ignores
  unknown keywords.

## Decisions from review

| Question | Decision |
|---|---|
| Names | `EventSchema<T>` is the producer's base class; the built model is `EventSchemaDefinition` (`FieldDefinition`, `ContextDefinition`) |
| Several events | One JSON Schema document per event; a collection is a JSON array of documents |
| Contexts in event schemas | **Relations only**: `Context(name)` with an optional `ReferencedBy(...)` (single or composite, EF Core style). A context's fields are described once, where its provider is registered (generated from `ContextProvider<T>`), not by each producer. Replaces the earlier `Context<T>(name, c => c.Field(...))` and `Many()` |
| Context references at run time | The engine resolves `ReferencedBy` and passes it to the provider (#93), so one provider serves several contexts/events (`fromAccount`/`toAccount`) |
| Per-event overrides of context fields | Later idea (ignore or relabel a context's fields for one event); in the vision's *Under consideration* |
| Cycles | Kept as `$ref` in JSON (from the exporter); read back as an object without fields |
| Generator | System.Text.Json's `JsonSchemaExporter` (no dependency; follows the producer's serialization) instead of hand-written inference or NJsonSchema (Newtonsoft, older drafts) |
| Serializer options | `JsonSerializerDefaults.Web` by default, overridable |
| json-everything (JsonSchema.Net) | Evaluated and not used: its NuGet binaries come with an "Open Source Maintenance Fee" agreement (a monthly fee for revenue-generating organisations above US$10,000), which RuleLoom's users would inherit; its generator doesn't follow System.Text.Json's contract; and the part it would replace (reading JSON back) is about 80 lines. Worth revisiting (or Corvus.JsonSchema, Apache-2.0) when incoming events are validated against schemas |
| Labels | Only configured labels; no automatic labels from names (and no Humanizer): a guessed label rarely matches the business term, and it was code to maintain |
| Typed model vs document lookup | Keep the typed field tree (`FieldDefinition` with nested `Fields`/`Items`), which C# consumers can iterate. A document-only design with a path lookup was tried: it didn't reduce code and dropped the tree |

## Deviations

Fixes from the code review of PR #100 (before merge):

- Sibling `$ref`s from the exporter are inlined (only cycle references remain), fixing list fields reached through a
  second property being read as objects and ignored fields leaving dangling references.
- Untyped properties (`object`, `JsonElement`, `JsonNode`) no longer make `Build()` throw: new `FieldType.Any`; arrays
  without `items` have items of any value.
- Nullable string enums are nullable; numbers written as strings are strings.
- Every malformed document throws `JsonException`.
- Configuring a field inside an ignored one throws a clear error regardless of order.
- Assembly scans skip open generic schema classes.
- `FieldDefinition` and `ContextReference` have structural equality.
- Prepared serializer options are cached per options instance.

Fixes from the second review:

- A labelled untyped field stays nullable; named floating-point literals stay numbers.
- Only read-only serializer options are cached (later changes to mutable options are followed).
- Composite reference parts that collide after the naming policy throw a clear error naming the context.
- No limit on inlined repeats (they're bounded by the type graph, since cycles aren't inlined).
- `Parse` enforces the builder's rules: a non-empty event type, unique context names (ignoring case).
- Cleanups: one helper formats property paths, one set of write options, collections are read and written without copying
  each document.
